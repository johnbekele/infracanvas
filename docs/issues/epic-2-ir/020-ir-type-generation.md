### Epic

#3

### Context

The schema is the authority, but nothing reads JSON Schema at development time. The canvas, the code
generators, and the brain's agents all need the IR as native types, and hand-writing those types in
two languages reintroduces exactly the drift the schema was created to prevent: the schema would say
one thing, `packages/core` another, and `services/brain` a third, with the disagreement surfacing as
a validation failure in production rather than a red check.

Generated files are committed rather than produced at build time. The alternative, generating into
`dist/` during `pnpm build`, was rejected for two reasons. First, a reviewer cannot see what a schema
change did to the public surface, and the whole point of the version discipline in
`docs/issues/epic-2-ir/010-architecture-ir-schema.md` is that a breaking change is visible in the
diff. Second, `.github/workflows/gate-contract.yml` already implements the drift check as
"regenerate, then `git diff --exit-code`", which only means anything if the output is tracked.
Committed generated code costs a mechanical diff on every schema change and buys a reviewable one.

The Python side is generated with `datamodel-code-generator`, which is the maintained path from JSON
Schema to Pydantic v2 and understands `oneOf` with a `const` discriminator well enough to emit a
tagged union. The rejected alternative was writing a small Pydantic emitter in the same Node script:
it starts at fifty lines and grows every time the schema uses a keyword it has not seen, and a bug in
it looks exactly like a bug in the IR. Shelling out to `uv run --with datamodel-code-generator` means
the drift job needs `uv`, which is one step in the workflow and the same action already used by
Gate 3.

The generated Pydantic models are written into `services/brain/src/brain/ir/models.py` rather than
into a second Python distribution under `packages/ir-schema/python/`. The brain is the only Python
consumer, so a separate distribution buys nothing and costs a `pyproject.toml`, an editable install
in the brain's environment, and a packaging step in every workflow that touches Python. Generating
into the brain also means `mypy --strict` type-checks the models on every run, which is free
verification that the emitted code is well typed.

Spec: `docs/DELIVERY.md`

### Contract

`packages/ir-schema/scripts/generate.mjs` grows from emitting the version constant to emitting three
artefacts, and must be idempotent:

```javascript
// packages/ir-schema/scripts/generate.mjs
// 1. src/generated/ir-version.ts   - IR_VERSION, IR_SCHEMA_ID   (exists already)
// 2. src/generated/types.ts        - json-schema-to-typescript
// 3. ../../services/brain/src/brain/ir/models.py - datamodel-code-generator via uv
//
// Every output begins with:
//   AUTOGENERATED FROM packages/ir-schema/schema/architecture-ir.schema.json - DO NOT EDIT
//   Regenerate with: pnpm --filter @infracanvas/ir-schema generate
// Exits non-zero with the schema path and parser message when the schema does not compile.
```

The TypeScript surface, re-exported from `packages/ir-schema/src/index.ts` so consumers never import
from `generated/` directly:

```typescript
export interface ArchitectureIr {
  irVersion: string;
  name: string;
  provider: 'aws';
  region: string;
  nodes: IrNode[];
  edges: IrEdge[];
  presentation?: IrPresentation;
}

export type IrNode = VpcNode | SubnetNode | PendingContractNode;
export type ResourceKind = IrNode['kind'];

export interface VpcNode {
  id: string;
  kind: 'vpc';
  name: string;
  parent?: string | null;
  layout?: IrLayout;
  params: { cidrBlock: string; enableDnsHostnames?: boolean; enableDnsSupport?: boolean };
}

export interface IrEdge {
  id: string;
  kind: 'connects' | 'depends_on' | 'routes_to';
  source: string;
  target: string;
  label?: string;
  sourceHandle?: string;
  targetHandle?: string;
}
```

The Python surface:

```python
# services/brain/src/brain/ir/models.py  (generated)
class VpcParams(BaseModel):
    model_config = ConfigDict(extra="forbid")
    cidr_block: str = Field(alias="cidrBlock")
    ...

class VpcNode(BaseModel):
    kind: Literal["vpc"]
    ...

IrNode = Annotated[VpcNode | SubnetNode | PendingContractNode, Field(discriminator="kind")]

class ArchitectureIr(BaseModel):
    model_config = ConfigDict(extra="forbid", populate_by_name=True)
    ir_version: str = Field(alias="irVersion")
    nodes: list[IrNode]
    edges: list[IrEdge]
```

Field names are snake_case with a camelCase alias, because the wire format is the JSON the canvas
sends and PEP 8 is what the brain's own code reads. `populate_by_name` keeps both accepted.

The parity test is the one that matters, and it lives on the Python side because that is where the
two representations can be compared against the same fixture:

```python
# services/brain/tests/test_ir_models.py
@pytest.mark.parametrize("fixture", sorted(FIXTURES.glob("*.json")))
def test_pydantic_accepts_every_fixture_the_schema_accepts(fixture: Path) -> None: ...

@pytest.mark.parametrize("fixture", sorted((FIXTURES / "invalid").glob("*.json")))
def test_pydantic_rejects_every_fixture_the_schema_rejects(fixture: Path) -> None: ...
```

`test_pydantic_rejects_every_fixture_the_schema_rejects` excludes the fixtures that fail only on the
referential rules `validateIr` adds on top of the schema (`unknown-parent.json`, `parent-cycle.json`,
`duplicate-node-id.json`), because Pydantic checks shape and not graph consistency. The exclusion is
a named list in the test, not a `try/except`, so adding a fixture cannot silently widen it.

Workflow change: the `schema-drift` job in `.github/workflows/gate-contract.yml` gains an
`astral-sh/setup-uv` step before the regeneration step, pinned to the same SHA already used in
`gate-test.yml`. Nothing else in that file changes.

### Acceptance Criteria

- [ ] `pnpm --filter @infracanvas/ir-schema generate` run twice leaves the working tree clean
- [ ] Regenerating after adding a required property to the schema changes both `types.ts` and `models.py`
- [ ] Every generated file carries the do-not-edit header naming the schema and the regeneration command
- [ ] `IrNode` is a discriminated union on `kind` in TypeScript, so a `switch` on `kind` narrows `params`
- [ ] `ArchitectureIr.model_validate` rejects a document with an unknown top-level key
- [ ] Assigning a `params` object to the wrong `kind` is a TypeScript error, asserted by a `@ts-expect-error` line
- [ ] `uv run --directory services/brain mypy` passes with the generated module included
- [ ] The generator exits non-zero with the offending path when the schema is not valid JSON Schema
- [ ] Gate 4's `schema-drift` job fails on a hand-edited generated file

### Required Tests

- `regenerating from an unchanged schema produces no diff`
- `every generated file carries the do not edit header`
- `switching on kind narrows the params type` - a `@ts-expect-error` assertion on the wrong branch
- `test_pydantic_accepts_every_fixture_the_schema_accepts`
- `test_pydantic_rejects_every_fixture_the_schema_rejects`
- `test_pydantic_rejects_an_unknown_top_level_key`
- `test_camel_case_and_snake_case_field_names_both_parse`
- `generator exits non zero when the schema does not compile`
- `every resource kind in the schema appears in the generated python union`

### Performance Budget

Generation completes in under 25 seconds from a warm `uv` cache, measured by `time pnpm --filter
@infracanvas/ir-schema generate`. It adds under 60 seconds to Gate 4, which is the cost of the `uv`
setup step plus generation.

### Out of Scope

- Do not hand-edit the generated files to improve a name. Change the schema or the generator
- Do not change the schema in this issue; a schema change here would need a version bump and would
  make the drift diff impossible to review
- Do not add IR handling to `services/brain/src/brain/app.py`. This issue lands models, not routes
- Do not publish `@infracanvas/ir-schema` to npm or the models to PyPI
- Do not touch the `openapi-drift`, `migrations`, or `destructive-ddl` jobs in `gate-contract.yml`
